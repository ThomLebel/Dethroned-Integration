Ajouter du contenu

Procédures pour étendre le système sans modifier l'existant. Chaque type de contenu a son propre flux d'ajout dans l'architecture Manager Graph.

Principe : ajouter = créer des fichiers. Ne jamais modifier les fichiers de base existants sauf si le type d'événement est nouveau.

Ajouter un Déclencheur de Base

Règle : créer un .tres suffit si l'événement existe déjà dans les event_ids reconnus par SkillManager. Nouveau type d'événement → ajouter process_event("nouveau_type", ctx) dans le manager source + enrichissement dans ContextBuilder.
  • Créer res://skills/data/triggers/base/DB-XXX_nom.tres de type TriggerData
  • Renseigner trigger_type: "base", event_ids, loc_type, cooldown, tags
  • Assembler les conditions depuis la bibliothèque dans l'inspecteur (ordre : vérifications → RecordTimestamp en dernier si temporel)
  • Vérifier que tous les tags utilisés existent dans liste_tags_v4.md
  • Vérifier la compatibilité loc_type / #req_ de l'effet associé via systeme_ciblage_v1.md

Ajouter un Déclencheur Avancé

Contrainte obligatoire : tout Déclencheur Avancé doit avoir CheckBuildTag { required_tag } comme dernière condition. Sans cette condition, il serait proposé à tous les builds indépendamment de leur compatibilité.
  • Créer res://skills/data/triggers/advanced/DA-XXX_nom.tres de type TriggerData
  • Renseigner trigger_type: "advanced" — ne sera jamais proposé comme Set de Base
  • Identifier le ou les tags de build requis — documenter dans la description du .tres
  • Ajouter CheckBuildTag { required_tag: "#tag_requis" } en dernière condition
  • L'événement déclencheur peut être un événement secondaire émis par un behaviour (ex. "elemental_synergy", "invocation_placed")

Ajouter un Effet

  • Créer res://skills/data/effects/FAMILLE/E-XX-YY_nom.tres de type EffectData
  • Choisir la target_mode (#req_cible, #req_point, #req_soi, #req_global) — vérifier compatibilité avec les déclencheurs cibles
  • Assembler les behaviours depuis la bibliothèque dans l'inspecteur — jamais de condition dans un effet
  • Si l'effet applique un état élémentaire : utiliser ApplyElementalState, pas ApplyDotStatus
  • Si un nouveau behaviour est nécessaire : créer res://skills/behaviours/CATEGORIE/nom_behaviour.gd qui étend EffectBehaviour — uniquement si réutilisable par ≥ 3 effets

Ajouter un État Élémentaire

Il existe 5 états élémentaires définis : Chauffé · Intoxiqué · Électrifié · Mouillé · Brisé. Ajouter un 6e état est une décision de design majeure — valider d'abord contre la table des synergies dans effets_catalogue_v4.md.
  • Ajouter l'état dans StatusManager._elemental_states avec sa durée de base et son malus
  • Étendre la table de synergies dans StatusManager.SYNERGY_TABLE pour toutes les paires impliquant le nouvel état
  • Créer un tag spécifique dans liste_tags_v4.md (niveau Spécifique, famille DoT & Érosion)
  • Ajouter l'atténuation boss/mini-boss dans DifficultyManager.ELEMENTAL_ATTENUATION

Ajouter un Manager

  • Déterminer la couche (N) selon les responsabilités et les dépendances — voir la Hiérarchie des managers
  • Copier le template template_manager.gd
  • Déclarer en Autoload dans l'ordre de sa couche (voir Intégration Godot)
  • Documenter les méthodes publiques, les managers appelés, et les managers qui peuvent l'appeler
  • Si le manager émet des événements vers SkillManager : documenter le type d'événement et les clés ctx ajoutées dans Flux d'un événement

Ajouter un Ennemi

  • Créer EnemyData.tres avec stats (PV, vitesse, masse, virage, coeff_ACC, coeff_DEF), type IA, affinités, compétences
  • Utiliser la scène enemy_base.tscn — pas de nouvelle scène sauf cas exceptionnel
  • Compétences ennemies : un TriggerData + un EffectData par compétence — même pipeline que le joueur
  • Règle de rareté : rareté Effet ≤ rareté Déclencheur dans le même set
  • Passer par EnemyManager.spawn(data) — ne jamais instancier directement
  • Vérifier que l'espèce n'est pas jouable (règle d'or)

Ajouter une Relique

  • Créer RelicData.tres avec id, type (faible/forte), tags, description bonus, description malus
  • Implémenter l'effet dans BuildManager.apply_relic(relic_data) — les reliques modifient des paramètres lus par les managers, jamais directement le gameplay
  • Si la relique réagit à un événement de jeu (ex. "à chaque heurt") : enregistrer un observateur dans SkillManager._relic_observers
  • Vérifier que tous les tags référencés existent dans liste_tags_v4.md
  • Ajouter au reliques_v7.md et au CSV correspondant

Ajouter une page à ce guide

  • Créer pages/mon-sujet.html — fragment HTML avec registerSearchEntries()
  • Éditer nav.json — ou utiliser l'éditeur ✏️ Nav dans la sidebar
  • Tester en local avec python3 -m http.server 8080
  • Pour les outils interactifs : consulter le Prompt d'intégration →
